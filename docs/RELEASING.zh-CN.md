# 一键提交源码并发布 2.4.2 / 2.4.3

脚本默认会执行真实的 commit、打标签、push 和 GitHub Release 发布。只有 `-DryRun` 是离线只读预览。

本次准备脚本时没有替你提交、推送、打标签或创建 Release。以下操作交由仓库所有者运行。

## 运行前

- 已安装 Git for Windows 和 Python 3，并配置自己的 Git 作者名称、邮箱。
- 当前分支是 `main`，origin 为 `https://github.com/zsnmsl/WanderTrace.git` 或同仓库的 SSH 地址。
- 两个已构建 APK 保留在本机 `releases/` 目录，文件名与 `scripts/release-plan.json` 一致。
- 没有手工暂存的文件；运行前先阅读两份更新说明并检查本地改动。

先在项目根目录预览：

```powershell
./scripts/publish-releases.ps1 -DryRun
```

确认后，双击根目录的 **`release.bat`**。也可在 PowerShell 执行：

```powershell
./scripts/publish-releases.ps1
```

发布时使用 Git Credential Manager 中的 GitHub 登录。若权限不足，可以在本机环境设置具有仓库 **Contents: write** 权限的 `GH_TOKEN`，不要写入脚本、更新说明或 Git 仓库。脚本不会输出或保存 Token。

## 脚本做什么

1. 验证 APK 的真实包名、内部版本、SHA-256、原生库，以及准备发布的源码指纹。
2. 在原始提交基础上，从当前工作区的步频修复文件构建 **2.4.2 源码提交**；保留这一版的旧速度 / GPS 模型，不混入 2.4.3 配速功能。
3. 提交其余 **2.4.3 源码、提交 / 发布工具和文档**。工作区源码始终保留为 2.4.3，不通过回滚或覆盖文件来切换版本。
4. 创建带更新说明的 `v2.4.2`、`v2.4.3` 标签，原子推送 `main` 和这两个标签。
5. 分别创建 Release 草稿，上传对应 APK 和分版本 SHA-256 文件，验证上传摘要后再发布。将 **2.4.3** 标记为 Latest，2.4.2 不设为 Latest。

源码提交不会包含本机 `releases/`、构建目录、生成的 `.so` 或凭据文件；APK 作为 GitHub Release 附件上传。

## 更新说明

- [2.4.2：步频计时和事件发送修复](release-notes/v2.4.2.md)
- [2.4.3：配速显示、速度变化与 GPS 漂移](release-notes/v2.4.3.md)

每份说明包含英语、中文和日语摘要，并写明本地测试范围、未完成的真机验证、开发证书签名和原生库加载条件。

## 中断、重试与限制

- 网络中断后可重跑：已经匹配的 Release 附件会复用，草稿会继续上传；不会重复建立已存在的标签或覆盖不同的附件。
- 同名附件校验值不同、已发布说明不同、标签指向不同版本时会停止，需要人工检查。
- 若远端分支领先或历史不一致，脚本停止，不自动合并、不强推。处理完同步问题后再运行。
- 这个发布计划绑定当前两份 APK、对应源码指纹和原始提交。**请先运行本发布脚本完成两版拆分，再用日常 `commit.bat` 提交后续代码**。如果先手工提交了整份 2.4.3 源码，或又修改了应用 / 原生代码，脚本会要求重新核对计划，不会擅自改写历史或给旧 APK 配上新代码。
- 如果 Git 提交本身失败，已暂存的版本快照可能保留在暂存区。先查看 `git diff --cached`，处理作者、签名或提交 Hook 等错误后，再人工提交 / 取消暂存并重试；不要使用强制重置来清理工作区。

以后普通代码更新仍可使用 `commit.bat`。发布其他版本前，需要重新构建、编写对应说明并审查发布计划，不能直接沿用这两版的版本号和校验值。
